# Order Experience V2 — 6 October 2026

Branch `feature/3l-order-experience-v2`, from the accepted visual commit `a3b9995`.
Not deployed. Validated only against local fixture servers with a fake payment
provider: no real payment, WhatsApp message or customer email was sent.

## Public order numbers

- `Order.publicOrderNumber` is a separate integer shown as `#001` (`shared/order-number.ts`).
  The internal `TL-XXXXXXXX` id is unchanged and remains the only key used for
  Paymennt (`orderId`, `requestId`), idempotency, lookups and audit.
- Issued by `assignPublicOrderNumber` in the same store transaction that first
  makes an order paid. Unpaid, failed and abandoned checkouts never consume one.
  Retried payments, repeated webhooks and reconciliations return the same number.
- The store serialises writers with SQLite `BEGIN IMMEDIATE`; the sequence
  (`State.orderNumberSequence`) only increases and never falls behind a number
  already present on an order, so numbers are unique and never reused.

### Migration strategy for existing orders

No data migration runs at startup. Orders paid before this release have no
public number and keep showing their internal reference everywhere
(`orderReference()` falls back to the id). The first order paid after release
is `#001`. Nothing in payment history is renumbered or rewritten.

Backfilling historical paid orders in `paidAt` order is possible but writes to
Production data; it is a separate, explicitly authorised step, not part of this
release.

## Checkout

- First and last name are captured and stored separately
  (`customerDetails.firstName/lastName`) and sent to Paymennt as given. A single
  legacy `name` is still accepted from older clients and saved drafts.
- Delivery area is a typeahead (`src/brand/AreaField.tsx`, `shared/area-search.ts`):
  prefix, alias and misspelling matching over the approved areas only. The form
  value is always a canonical zone id; the server re-validates it and takes the
  minimum from that zone. Free text cannot be submitted.
- Billing: "same as delivery" stays the default for delivery. Pickup asks for
  the Paymennt minimum only — street and city; the name comes from the contact
  details and the country is fixed to the UAE. The shop's address is never used
  as a customer's billing address. Paymennt's published `/checkout/web` schema
  requires `billingAddress` (name, address1, city, country).
- Pickup point is shown as "3L Pastelerías" (`shared/pickup-location.ts`).
  Legal pages keep the legal entity.
- After 21:00 Dubai, reaching or choosing a closed date opens a dialog offering
  the earliest date the server accepts. It is shown once per evening on reaching
  the date and whenever a closed date is attempted; dismissing it changes
  nothing and the server rejects closed dates regardless.

## Notifications

- Internal WhatsApp (existing ORDER_PAID outbox): one row per configured
  recipient — Liza, plus the 3L Manager when `WHATSAPP_MANAGER_PHONE` is set.
  Rows stay `pending-whatsapp-delivery` while `META_OUTBOUND_ENABLED=false`.
- Customer email (`server/domain/customer-notifications.ts`): a durable row per
  (order, event), written in the same transaction as the operator's transition.

  | Transition | Applies to | Event |
  |---|---|---|
  | Confirmed → Production | delivery and pickup | `ORDER_PRODUCTION_STARTED` |
  | Production → Ready | pickup only | `ORDER_READY_FOR_PICKUP` |
  | Ready → Out for Delivery | delivery only | `ORDER_OUT_FOR_DELIVERY` |

- Delivery is by Resend (`server/adapters/resend.ts`) behind the
  `CustomerEmailProvider` interface. It is constructed only when
  `CUSTOMER_EMAIL_ENABLED=true`, `RESEND_API_KEY` and `CUSTOMER_EMAIL_FROM` are
  all set; otherwise rows stay `pending` and are shown in Operations as
  "proveedor de email no configurado". The outbox row id is the Resend
  `Idempotency-Key`. A row left `sending` by a crash is marked `failed` for
  review, never resent automatically.
- Email copy is English only; no support address is included.

## Apex domain

The app now answers `GET`/`HEAD` on the bare host of `APP_ORIGIN` with a 301 to
the `www` origin, keeping path and query. This only takes effect once DNS sends
`3ldubai.ae` to Railway. DNS has not been changed: the apex still points at the
registrar's parking server. Railway has no static IP, so the registrar must
offer ALIAS/ANAME/CNAME flattening (AEserver documents A/AAAA at the root and
asks customers to contact support for root aliasing) or its own HTTPS
forwarding. Nameservers, MX and the `www` CNAME stay as they are.
