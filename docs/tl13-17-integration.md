## Paymennt

Official sources inspected 2026-09-07: [payment-link flow](https://docs.paymennt.com/docs/payment/links), [OpenAPI contract](https://docs.paymennt.com/openapi/paymennt.yaml). `PaymenntProvider` implements `POST /checkout/link`, `GET /checkout/{checkoutId}` and recovery through `GET /checkout?requestId=...`. Base URL is allowlisted: test `https://api.test.paymennt.com/mer/v2.0`, live `https://api.paymennt.com/mer/v2.0`. Runtime configuration enables **test only**. Headers are `X-Paymennt-Api-Key` and `X-Paymennt-Api-Secret`; credentials never cross the server boundary. Domain integer fils convert to decimal AED only at the adapter. Link creation includes internal requestId/paymentId, orderId, description, amount/currency and disables provider SMS/email. Customer/contact data are optional in this official link schema and omitted.

`PaymentProvider` remains interchangeable with MockPaymentProvider. Checkout statuses preserve pending, authorized, pending_confirmation, paid, failed, cancelled, expired, refunded, partially_refunded and chargeback. AUTHORIZED never confirms an order. No capture/refund API mutation is implemented. Verified refund/dispute states block subsequent fulfillment transitions and require operator review; they do not rewrite delivery history.

`Check Status` invokes an authenticated server operation, fetches authoritative checkout, checks checkout ID + requestId + orderId + integer amount + AED, then transactionally records status. Duplicate reads cannot duplicate Paid/Confirmed transitions. Previously settled payments never regress to pending/failed; older results are recorded for review. `paidAt` is our first authoritative observation timestamp, not a fabricated processor settlement timestamp. The inspected checkout schema does not expose a distinct transaction ID or expiry timestamp: those are not fabricated from the checkout ID. Checkout reference/ID, raw status, URL, created/updated/lastReconciledAt and audit history are stored. A lost POST response becomes unknown; recovery searches requestId, requires exactly one result and fetches it again. An empty/ambiguous result never triggers another POST automatically.

**BLOCKED — PROVIDER CONTRACT:** the official OpenAPI exposes webhook registration `/webhooks` and returns `hmacKey`, but the inspected sources do not specify notification payload, signature header, algorithm encoding or signed-byte construction. Do not assume Meta's signature scheme applies. Paymennt's live notification route returns 503 and its default verifier rejects every input. To complete: obtain official merchant webhook documentation and a signed test vector, implement normalization/verifier, durable reconciliation scheduling and replay/timeout tests. The current release therefore does **not** claim automatic Paymennt webhook integration. Manual Check Status is functional against mocked official HTTP responses, not merchant-tested. No request has been sent to Paymennt with real credentials.

## Meta WhatsApp

Sources: Meta's maintained [messages collection](https://www.postman.com/meta/whatsapp-business-platform/folder/o48mro7/messages), [payload reference](https://www.postman.com/meta/whatsapp-business-platform/folder/tduohwq/webhook-payload-reference), [template request](https://www.postman.com/meta/whatsapp-business-platform/request/o65u5m5/send-message-template-text). Adapter uses configurable supported Graph version, `/{phone_number_id}/messages`, Bearer token and WhatsApp messaging payload. One to three configured operational aliases map to actual phone_number_id/WABA/phone combinations, so WA1 can be activated before real WA2/WA3 identifiers exist. Replies compare both stored source alias and phone; no fallback number exists.

GET `/api/webhooks/whatsapp` checks subscribe mode + verify token and returns challenge. POST checks raw-body HMAC-SHA256 (`X-Hub-Signature-256`, app secret) before parsing all entries/changes/messages/statuses. Normalized text/GPS/unsupported messages retain provider timestamps. Unknown status types are ignored; unknown configured account/number is rejected. Accepted batches persist before HTTP acknowledgment; background processing is idempotent. Early delivery statuses retry against the stored provider message ID; exhausted inbox attempts remain visible in health counts for investigation. Unsupported media is represented as unsupported, not downloaded or interpreted.

Persistent outgoing jobs send outside SQLite transactions. Provider failures distinguish definite rejection from unknown outcomes. Meta has no assumed idempotent send guarantee: timeouts/server uncertainty do not automatically resend. Definite rejections expose a manual retry after correcting configuration. Free text requires a customer message within 24 hours; otherwise the adapter rejects unless an explicitly configured template is used. `META_PAYMENT_TEMPLATE_JSON` may specify an approved payment template name/language whose two body parameters are amount in AED, then the full payment URL. Payment messages use it outside the service window only when configured; ordinary free text remains blocked. Confirm merchant approval and exact template structure before configuration. Generic operator template browsing is outside this payment-focused sprint.

**BLOCKED — EXTERNAL CREDENTIALS:** verify the customer's current Business App/API/BSP/coexistence setup, ownership of three numbers, WABA IDs, business verification, app subscriptions/permissions, system-user token and supported Graph version. Obtain approved template names/languages/parameters and test recipient consent. Existing conversation history is not imported or promised. Real onboarding and delivery receipts remain untested.

## Runtime, auth and operations

Single Node process + SQLite WAL on local persistent disk. No shared network filesystem, multiple app replicas or ephemeral DB. Integration requires a new absolute database path and HTTPS origin; startup rejects sandbox DB promotion and live Paymennt mode. No migration of fictitious orders. Original storefront remains a labelled demo and is not the operational source of payment truth.

Users are configured through `OPERATOR_USERS_JSON` with scrypt hashes (script provided), roles admin/manager/operator; legacy agent remains supported. Admin edits zones; manager reassigns conversations and reconciles payments; operators act on assigned open conversations/orders. Session cookies are HttpOnly/Secure/SameSite=Strict, expire after eight hours and invalidate on restart/logout. Login and all state-changing internal routes check configured Origin. API payloads use Zod, version checks and command idempotency. All views expose operational records to authenticated staff; this is a single-business deployment, not a multi-tenant isolation model. Protect the whole origin with HTTPS reverse proxy; bind Node to loopback/private network. Users/providers are deployment configuration, no public management API.

`GET /api/health` is liveness; `/api/ready` checks local storage and reports pilotReady=false (does not pretend to probe provider accounts). Workspace exposes failed inbox counts and unfinished outbox jobs. `SAFE_LOGS=true` emits allowlisted event/status/count/attempt/correlation fields; no bodies, phone numbers, addresses, coordinates, URLs or credentials. API responses carry X-Request-Id; outgoing jobs preserve originating correlation IDs. Rate limits: login 10/min/source IP, API 300/min/source IP. Behind a proxy, all requests may share its IP; configure perimeter per-client limits and burst capacity. Do not blindly trust client-supplied forwarded headers. Alert on unknown jobs, failed inbox processing, repeated reconciliation mismatch, 401/429/5xx and backup failure.

Deployment preparation: Node >=22.13 (validated Node 26.4), install locked dependencies, `npm run build`, `npm start`. Required env in `.env.example`; process environment is used, not client VITE variables. Keep DB/backups outside static dist. HTTPS reverse proxy terminates TLS and forwards to private Node; health checks target Node. Preserved Sites Worker serves static assets only and cannot host this backend. No deployment was attempted.

Move to Postgres when multiple nodes/HA are required, operator load causes measurable BEGIN IMMEDIATE contention, state document size/latency becomes operationally significant, or stronger recovery requirements arise. Migration: freeze writers, verified backup, normalize conversations/messages/orders/payments/inbox/outbox/receipts/audit, carry unique provider IDs/idempotency keys and optimistic versions, compare totals/counts, rehearse restore, then controlled cutover. Current snapshot store is intentionally bounded to a controlled single-node pilot.

## Safe backup / restore

Run `node scripts/backup.mjs ABSOLUTE_DB NEW_BACKUP_PATH` from a trusted host. Uses Node SQLite online backup API (includes committed WAL data), refuses overwrite, verifies integrity and sets mode 0600. Store backups on encrypted restricted storage outside the app volume; schedule and retention are deployment responsibilities, not configured here. Suggested pilot target for owner approval: hourly backups, 24-hour/7-day retention, daily off-volume copy; agree RPO/RTO before launch.

Restore rehearsal: stop app and all writers; preserve failed database plus WAL/SHM for investigation; verify backup integrity; restore backup into a **new empty directory** with correct ownership/0600 permissions; point DB_PATH there; start one process; check readiness, order/payment totals and command receipts, inspect unknown/processing jobs before allowing sends. Never mix restored DB with old WAL/SHM. Test restore in an isolated test environment first, with provider access disabled; never replay live jobs in a rehearsal. Automated test restores data/receipts from a live WAL-backed source. Actual hosting volume, encrypted off-host retention and operator restore rehearsal remain external UAT requirements.
